## 二、2026-10-09 修复与新增设施

### H1（已修复）· pak CoW 在网络模式实际失效

`FInPlacePakPatcher` 主循环对**每个**远端条目先无条件 `FetchRemoteBytes`、**然后**才判
Same（Same 分支丢弃取来的字节）。而下载阶段只预取"变化条目"覆盖的窗口
（`FUpdateOrchestrator.cpp`："Same entries are verified locally: zero fetch"）——
网络模式下 Same 条目的窗口不在缓存 → 取数必败 → 整个 CoW patch 返回 false →
**静默回退全容器下载 + 整文件重写**；本地模式则每次白读全容器字节（只统计写的
stats 完全看不见）。对照 `FInPlaceIoStorePatcher` 先判后取，证明是 bug 非设计。

**修复**：Same 判断整段前移（判据 = 本地内置哈希 vs 清单 SHA1，与取来的字节无关，
前移零语义变化）。**证据**（downloadtest bigpak 场景，4.3MB 多窗口合成 pak 改 1 个
100KB 条目）：修复后 `4 same (zero movement, 4,194,576 B reused) / 1 appended,
102,400 B written`、per-patch `disk read 576.4 KB / chunk loads 1`、整轮
`net down 473.9 KB`；重跑收敛 `chunk loads 0 / net 0 / write 3.8 KB`（状态 JSON）。
修复前的旧顺序该场景 load ≥7、重下整容器 4.3MB+、整文件重写——两个断言都会挂。

**测试逃逸机理**（记录以免重犯）：旧 netdelta 场景的 fixture pak 只有 939B =
**单个 CDC 窗口**（Min 256KB），Same 与 Changed 条目共享同一窗口，恰好全部命中缓存。
bigpak 场景（FastCDC 实测切 7 个 chunk）把这个盲区封死。

### H2（已修复）· 下载执行器丢弃取消句柄

`FDownloadExecutor::IssueSegment` 未把 `DownloadRangeAsync` 的返回值存进
`S.CancelHandle` → `Cancel()` / 析构里的 `CancelDownload` 全是空操作，HTTP 传输
照跑到完。**修复**：接上句柄；H5 场景补断言
`[PASS] the in-flight transport request received CancelDownload`（修复前必挂）。

### I/O 统计系统（FIOStats，防复发设施）

- `UnrealGamePatcherCore/Stats/FIOStats.h/.cpp`：进程级原子计数——磁盘读/写（字节+次数）、
  网络下行/上行、压缩/解压（入/出+次数）、chunk 库加载次数（含失败尝试）、哈希字节数。
  `FormatSummary` 一行摘要；`FormatDelta` 供 per-patch 增量报告。
- **插桩点**：FChunkDataLoader、FPakReader、FPakWriter、FPakRecovery（恢复扫描的
  footer/index 读）、FIoStoreReader/Writer、FPatcherHash::FileSHA1Hex、FChunkAssembler、
  JsonIo::WriteJsonFileAtomic、FDownloadManager（网络字节+staging 写+缓存校验读）、
  orchestrator（manifest 拉取/ReadFileRange/WriteAtomic）、ingest（staged 读取）、
  differ（拷贝）。
- **打印**：orchestrator 在 update（成功/失败/check-only）与 compact 结束打印全量摘要
  并写入 `FUpdateStats::IOStats`（可断言）；两个原地 patcher 打印 per-patch 增量。
  例（perftest 增量更新）：`disk read 47.4 KB (4 ops) | disk write 55.5 KB (6 ops) |
  net down 0 B | chunk loads 1 | hashed 38.1 KB`——**小增量必须是小数字，出现容器级
  体积 = 发生了静默回退**，一行揪出。
- **回归**：downloadtest bigpak（上述）+ H5 传输取消断言；15/15 套件全绿。

## 四、开放发现 · Low

第四轮盲评 Low（复核确认仍开放）：

- **L1** 恢复扫描窗口跨界 magic 漏检（`FPakRecovery.cpp` 清窗不重叠）→ 幸存 footer 恰好
  跨界时 Unrecoverable → pak 被删全量重建。方向安全（fail-safe），加 3 字节重叠即可。
- **L2** 恢复前置步 Unrecoverable pak 的 `DeleteFile` 返回值未检查；且会删除不在清单里的
  用户 pak（mod 包）——"更新器是唯一启动门"模型自洽，破坏性范围建议在 README 明示
  （stray 文件策略同理：信任模式巡检把索引+远端都没有的文件当 Removed 删除）。
- **L3** ingest 对读不到内置哈希的 pak 条目静默落全零 SHA1 → 该条目永远判 Changed，
  容器每轮重写（幂等但白费）；应硬失败。
- **L4** `FPakWriter` 洞放置无 `hole.End <= FileSize` 钳制（= 历史 M21）：现调用方算得对，
  防御未来调用方（洞越 EOF 时 Commit Stage 2 会覆盖洞内 payload）。
- **L5** 本地 pak 提取的 `OffsetInFile` 不含 entry header（ingest 侧含）——本地侧该字段
  无人消费，语义不一致迟早埋雷，对齐或删。
- **L6** selfCheck 哈希绑定 TCHAR 宽度（UTF-16 码元）——跨平台哈希不同；Windows-only
  下无碍，移植时改对 UTF-8 编码哈希。
- **L7** `AtomicReplaceFile` 的 rename-aside 与 move-in 之间掉电 = 目标暂缺（= 历史 M19 的
  残留窗口；失败路径已即时还原，崩溃路径无 `.prev` 回收方）。消费方均按 missing 自愈。
- **L8** 整文件 SHA1 终验在 executor 锁内、HTTP 线程执行——大文件阻塞全部 settle，
  与"100GB 级"目标冲突（chunk ≤4MB 现状不可见）。
- **L9** sidecar 洞字段不校验非负（ucas `PickHoleBase` 对负数运算可过界）。Load 处一行过滤。
- **L10** `verifyOnUpdate` 不验类型（字符串值静默当 false），与全库严格读取约定不一致。
- **L11** 文档漂移：套件计数（15 入口 / 14 套件 / "12 套件全绿"并存）、README 性能数字
  来自小 fixture（本轮已在文档更新中标注刻度条件）。

**历史 Minor 摘要**（2026-09-17 第二轮列的 ~50 项，未逐条重核；保留以防丢失）：
格式层——普通文件 SHA1 大小写不一致、state 洞负值、枚举外字段类型静默降级、`FSHA1::Update`
int32 截断、AssembleRange 越界回读、孤儿 utoc 重复下载；容器——压缩方法表满静默降级 raw、

删续传数据、Delete 目标 holes 残留、Rollback CopyFile 返回值忽略；Build——`Off < BufBase`

## 九、2026-10-15 第三轮：CDN index self-check 旧版布局假阳性（实战发现）

**现象**：2026-10-14 16:51 全新安装（rustfs CDN ugp-eds，player5，Debug exe）在
`resolved latest version 2.0.0` 后 23s 报 `FIndexManifest: '<index>' FAILED self-check
(tampered or corrupt; embedded 3b6b8ffabae449f6, recomputed 491925351327866a)`，
update 中止 [code 3]。重跑 recomputed 恒定 → 确定性，非传输损坏。

**定位**（三方比对 + 前像验证）：
1. CDN 对象 `index/2.0.0/UnrealGamePatcher.index.json` 与发布源
   `ElectricDreamsEnv/Saved/UGP_Cloud` 逐字节一致（MD5 42ed73c6…，4,046,427 B），
   文件内嵌哈希与报错 embedded 一致 → 客户端拿到的字节没问题，坏在重算侧。
2. 发布文件 mtime 2026-09-02，**pretty-print 格式（CRLF+tab 缩进）**、ioChunks 无
   metaHash/fileOffset/fileSize（与 Load 注释「older manifests predate it」吻合）。
3. Python 复算：`XXH3-64(UTF-16LE(原始文本剥离 selfCheck 键))` = `3b6b8ffabae449f6`
   **= embedded** → 文件完好，内嵌哈希是对旧版序列化字节算的。
4. 当前 `SerializeBody` 输出紧凑单行 + 对 ioChunks 恒写 metaHash/fileOffset/fileSize
   → Load 重序列化前像必然不同 → 假阳性。acc7588 重构（JsonIo.h 提取）本身逐字节
   等价，非根因；根因是「selfCheck 绑定当前序列化器字节」这一设计对历史发布件
   不兼容（10-11 那次 loaded-ok 跑的是本地 file:// 调试 CDN，新代码自己写的紧凑
   格式，故从未暴露）。

**修复**：`JsonIo.h` 新增 `MatchesRawBodySelfCheck`（从尾扫描 `"selfCheck"` 严格
形状 `,"selfCheck":"<16hex>"`，剥离后对原始文本重算 XXH3-64）；`FIndexManifest`
与 `FDeltaManifest` 的 Load 在 canonical 重算不匹配时回退该校验。篡改强度不变：
body 任一字节改动 raw 哈希即失配；仅放宽「必须与当前序列化器字节一致」这一
兼容性断言。新增 ~50 行，CDN 无需重发。

**收口自查（2026-10-15 提交质量轮）**：
- 循环终止边界修复：`MatchesRawBodySelfCheck` 的 FromEnd 扫描在匹配位置 0 时
  StartPos 会传成 INDEX_NONE(-1) 造成死循环（病态输入），改为显式递减游标。
- indextest 新增 §4e（11 项断言）：pretty 重排 + 哈希绑原始字节 → raw-body 回退
  加载成功；同文件篡改 contentVersion → 双路径均拒。53 → 64 项全绿。
- 顺手修 selftest（先于本轮即挂、与本次改动无关）：`FPatcherHashSelfTest.cpp`
  的 `CreateIoChunkId(..., ExternalFile)` 触发引擎 IoChunkId.h 的新增 checkSlow
  断言（162 行禁 ExternalFile、163 行禁 bulk 类型）——只在 Debug 构建暴露
  （Development 编译掉 checkSlow，历史 15/15 未踩到），测试意图是 hex 往返、
  类型无关，改用 `ExportBundleData`。
- 15 套件在最终 Debug 二进制上全量复跑：15/15 exit 0。

**教训**：内容寻址（self-check）哈希的前像绑定「当前规范化序列化器输出」时，
任何序列化器演进都会把历史发布件变成假阳性损坏。前像应取**文件自身字节**
（剥离校验字段），规范化重序列化只作为新版加速路径。
