# Android 启动前更新链审查（2026-11-11）

审查范围为最近 6 次提交 `990759b` 至 `dc5bdf9`。下列 3 个 P1 问题均由
`bc1da18` 引入，依据为静态调用链核对。

2026-11-12 已修复。API 35 模拟器验证了更新失败时回到已提交版本、旋转后在同一进程重试、转场后结束更新进程。发布中断通过构造第一次改名后的磁盘状态复现，旧索引和 Pak 的 SHA-256 一致。较早版本遗留的 Pending 事务仍需 CDN 在线才能在原路径恢复，期间启动门控保持关闭。详见 [Android 启动更新器](android-s1-runbook.md#android-启动更新器2026-11-12)。

## AND-01 · 进入游戏前跳过未完成事务恢复

位置为 `Build/Android/src/com/epicgames/unreal/patch/PatchActivity.java` 第 131–147 行。
已有安装在更新写入阶段被杀后，旧 `.ugp/index.json` 仍存在。再次启动时若 CDN
不可达，或者 CDN 目标版本回退到本地索引版本，Java 会直接进入 `GameActivity`。
`FUpdateOrchestrator` 内的 Pending 回滚与 Pak 尾部修复均被绕过，引擎可能挂载半更新容器。

应提供无需 CDN 的本地恢复入口，进入游戏前持安装锁完成恢复，再判断是否联网更新。
仅删除版本比较捷径仍不足够，当前编排器先读取远端清单，随后才恢复本地事务。

验收场景为已有 v1 安装、更新 v2 写入中强停、断网重启，以及 CDN 回退至 v1 后重启。
两种情况都须先恢复可挂载的一致安装。

## AND-02 · Activity 重建产生第二条引擎线程

位置为 `PatchActivity.java` 第 103–117 行，以及
`UnrealGamePatcherLib/Private/UnrealGamePatcherLib.cpp` 第 128–185 行。
旋转屏幕会重建 Activity。`quitSafely()` 不会中断已经执行的 `runFlow`，新实例又创建
worker，可能在安装锁获取前并发进入 `PreInit`。若旧尝试已失败，引擎仍保温，新的
worker 则与原来的 GameThread 身份不一致。

应让 worker 和更新状态跟随进程生命周期，Activity 重建后订阅现有任务。
仅对 apply 加安装锁无法保护发生在锁之前的引擎初始化。

验收场景为初始化中旋转、下载中旋转，以及失败停驻后旋转并重试。每个进程只允许
一个初始化过程与一条引擎工作线程。

## AND-03 · 成功关闭引擎后仍可复用更新器进程

位置为 `UnrealGamePatcherLib/Private/UnrealGamePatcherLib.cpp` 第 224–229 行，
以及 `PatchActivity.java` 第 210–211 行。成功路径卸载模块并调用 `AppExit`，
但 `bEngineReady` 仍为 true。Java 仅 `finish()`，系统可保留 `:ugppatch` 进程。
下次启动更新器且 CDN 发布新版本时，会跳过初始化，使用已经关闭的引擎。

应在确认游戏转场后结束专属更新进程，让下次更新使用新的引擎生命周期。
单独把 `bEngineReady` 置 false 会引入同进程二次 `PreInit`，不能作为修复。

验收场景为 v1 更新成功、保留更新器进程、发布 v2、再次打开更新入口。
必须使用新进程完成 v2 更新。

## iOS 移植约束

iOS 启动前更新视图必须在引擎挂载容器前完成更新，并复用 UGP 的下载、校验和事务实现。
初始化、重试与视图生命周期需要分别管理。进入引擎前必须完成本地恢复。
接入方案应明确单进程中 Core 初始化与正式引擎启动的衔接，避免重复 `PreInit`。
